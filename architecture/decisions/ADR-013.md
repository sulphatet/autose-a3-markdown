# ADR-013: The build check counts only lint errors the change introduces

**Status:** Accepted. Supersedes the `flake8 markdown passes` part of the stage 3 check in ADR-007.
**Date:** 2026-11-22
**Decision area:** D7, checks

## Context

ADR-007 made `flake8 markdown` passing part of the stage 3 build check, "the same lint as upstream CI".

The first real run ([run 44941261187](https://github.com/sulphatet/autose-a3-markdown/actions/runs/44941261187), issue #2) showed this was wrong:

- The build job runs Python 3.12. On 3.12, current flake8 reports four errors in `markdown/postprocessors.py:90`, on the **unchanged** base code: spaces inside an f-string, `{ base_placeholder }`. Upstream's lint job runs Python 3.11, where flake8 does not look inside f-strings, so upstream CI is green.
- The implementer's fix was correct: the diff touched only `fenced_code.py` and the changelog. But it failed the build check twice for errors it did not cause. The retries used up the token budget, and the run stopped at stage 3.
- The local dry run earlier had the same cause hidden inside it. There, the implementer "fixed" `postprocessors.py` to get past the check, which is why that dry run's diff contained an unrelated whitespace edit.

A check that fails on the base commit cannot tell a good change from a bad one.

## Decision

Before any agent runs, the orchestrator records a **lint baseline**: every `flake8 markdown` error on the base commit. Each error is keyed by file, error code, source line text and occurrence, not by line number, so edits elsewhere in the file do not shift it.

The stage 3 check fails only on errors that are not in the baseline. Pre-existing errors are counted in the artifact ("N pre-existing on the base commit ignored").

The implementer's input lists the pre-existing errors and says they are not its job.

## Alternatives considered

- **Run the build job on Python 3.11, like upstream lint.** Removes this particular difference, but the check would still break the next time a base commit is not lint-clean for any reason.
- **Lint only the changed files.** A change to `postprocessors.py` for a real reason would inherit the old errors and fail again.
- **Drop flake8 from stage 3 and rely on CI in stage 5.** CI catches it, but much later and at a higher cost, because a red CI needs a push and a CI round per attempt.

## Consequences

- The check now measures the change, not the state of the repository.
- An agent can still copy a pre-existing style problem into a new line. That is a new error and fails, which is the intended behaviour.
- This was found only by a real run. The dry run had passed, because the agent quietly worked around the check by touching an unrelated file. That deviation was visible in the stage 3 artifact, but nothing acted on it. This is a lesson for the report.
