# ADR-002: A coded state machine controls the flow

**Status:** Accepted
**Date:** 2026-11-21
**Decision area:** D2, control flow

## Context

The flow has loops: failing tests go back to implementation, repeated failures go back to design, and review findings go back to design or implementation, at most twice.

GitHub Actions jobs form a one-way graph (DAG). A job cannot loop back to an earlier job in the same run.

Maintainers must be able to predict what the bot will do, and a grader must be able to reproduce why a run took the path it did. An LLM that chooses the next step makes the path depend on sampling.

## Decision

A Python state machine (`workflow/autose/orchestrator.py`) owns all transitions. Agents produce artifacts. Deterministic checks (ADR-007) produce pass/fail, and the code chooses the next state from those results and from counters.

```
S1 Requirements --pass--> S2 Design --pass--> S3 Implement --build ok--> S4 Test
S4 --all pass--> S5 Release --PR open + CI green--> S6 Review (separate job)
S4 --fail, impl_attempts < 3--> S3 (with failure output)
S4 --fail, impl_attempts = 3, redesigns < 1--> S2 (with failure summary), impl_attempts reset
S4 --fail, budget used--> STOP (partial artifacts, reason)
S5 --CI red--> S3 (with failing job log), counts as an implementation attempt
S6 --approve--> END (human decides)
S6 --request_changes, kind=approach, round < 2--> new run from S2
S6 --request_changes, kind=code, round < 2--> new run from S3
S6 --request_changes, round = 2--> END (human decides, review says rounds used up)
any check fails with no budget left --> STOP, with the reason written in that stage's artifact
```

Stages 1 to 5 run in one job (`build`). Review runs in its own job (`review`, ADR-008). A review round that requests changes starts a new workflow run through `workflow_dispatch`, with inputs `issue`, `round` and `resume_from`. That is the only way to "loop" across Actions jobs.

The reviewer suggests whether a problem is about the approach or the code (`kind` in its JSON). The code makes the routing decision. If `kind` is missing or invalid, the code routes to S3 by default.

## Alternatives considered

- **LLM orchestrator that decides what to do next.** Flexible, but not deterministic, and it adds an agent whose own mistakes are hard to audit. Rejected.
- **One Actions job per stage, chained with `needs:`.** Each stage gets its own logs and permissions, which is attractive. But loops are impossible inside one run, so every retry would need a new dispatch, and each job pays setup time (checkout, Python, install). Kept only where isolation is required, which is the reviewer.
- **Everything in one job, including review.** Rejected: the reviewer would share the runner, files and token with the implementer (ADR-008).

## Consequences

- The path of every run is explained by `state.json` (ADR-004) and the check results, which makes `runs.md` and the sequence view easy to produce.
- The budgets are fixed in code: 3 implementation attempts per design, 1 redesign, and 2 review rounds. They cannot adapt to an unusually hard issue.
- The `kind` routing depends on the reviewer labelling its findings correctly. A wrong label sends work to the wrong stage, but it still costs at most one of the two rounds.

## How we will know if this is wrong

If many runs use up their budget on problems a human would recognise as needing a different route, for example a redesign after the first failure, the fixed rules are too rigid. This is visible in `results.csv` as the number of attempts per stage.
