# ADR-003: Agents hand over files, never conversations

**Status:** Accepted
**Date:** 2026-11-21
**Decision area:** D3, hand-offs

## Context

What each agent knows decides what it can get wrong. Too little context and the agent guesses. Too much and it inherits mistakes and biases from earlier stages, and the prompt gets longer and more expensive.

Issue text is written by anyone, so it is untrusted.

The repository the agents work in also contains this assignment's own material (`architecture/`, `experiment/`, `workflow/`, `results/`). That includes the ADRs and, later, the seeded PRs. An agent could read those and change its behaviour, or read the hidden tests.

## Decision

Agents receive a fixed set of files, and no other agent's conversation:

| Agent | Issue (raw) | spec.md | design.md | ARCHITECTURE.md | Repository | Feedback | Never sees |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Spec | yes | — | — | no | no | — | any code |
| Designer | yes | yes | — (writes it) | yes | read-only | failure summary on redesign; review findings when `kind=approach` | implementer or tester reasoning |
| Implementer | yes | yes | yes | yes | read/write (source) | test failure output, CI log, or review findings | tester reasoning, earlier implementer conversations |
| Tester | no | yes | yes | yes | read; writes `tests/` only | — | implementer reasoning, raw issue |
| Reviewer | yes | no | no | no | read at PR head | — | spec, design, test report, every agent's reasoning |

The implementer sees the raw issue as well as the spec. The issue sometimes has details the spec leaves out (an exact input that crashes, a traceback), and the implementer needs them. This increases its exposure to injected instructions, and ADR-009 contains that risk.

The tester does not see the raw issue. Its tests should follow the acceptance criteria in the spec, which is the contract the run committed to.

Before any agent runs, the orchestrator deletes `architecture/`, `experiment/`, `workflow/`, `results/`, `report.pdf` and the demo from the working copy. Hidden tests are never pushed to the repository while experiment runs are still going.

Every feedback message is built by code from structured data (test names, assertion text, CI job log tail, or review findings). It is not a free-form note from another agent.

## Alternatives considered

- **Pass full conversations forward.** Maximum context, but it breaks the closed-context rule of ADR-001, and the prompts grow with every stage.
- **Summaries written by the previous agent.** Shorter, but a summary is that agent's opinion of what matters. An error in the summary is invisible downstream. Artifacts are the summaries the brief already asks for, and they are checked.
- **Spec only, no raw issue for downstream agents.** Safest against injection. Rejected for the implementer, which loses concrete reproduction details. Kept for the tester.

## Consequences

- Each agent's input can be listed exactly in the run log, so a reader can see what an agent knew.
- When the spec misses something the issue says, the implementer may still handle it, but the tester will not test it. The reviewer, who reads only the issue, is the stage most likely to catch that gap.
- Deleting the assignment folders means agents cannot use the ADRs as hints. It also means `ARCHITECTURE.md` must be copied in from `workflow/` before the deletion.
