# ADR-008: Keeping the reviewer independent

**Status:** Accepted
**Date:** 2026-11-21
**Decision area:** D8, reviewer independence

## Context

A reviewer that agrees with the implementer adds nothing. Agreement can come from several sources:

- shared context (it read the implementer's reasoning),
- shared model (same blind spots),
- shared framing (a prompt that says the work was already tested and checked),
- no cost for approving.

The opposite failure is a reviewer told it must find problems. It invents problems, and those send the work around review rounds for no reason.

## Decision

The reviewer is separated on every axis we control:

| Axis | How it is separated |
| --- | --- |
| Job | `review` is its own Actions job, on a fresh runner, with a fresh checkout of the PR head commit. |
| Inputs | Only the issue (title + body), the PR diff, and the repository at the PR head. No spec, design, test report, `pr.md` body text, or any agent's conversation (ADR-003). |
| Model | `gemini-4-hydrogen`, a different model from the builders (ADR-006). |
| Prompt | Its own prompt. It does not say the code was generated, tested or checked. It asks the reviewer to work out from the issue alone what a correct change must do, then check the diff against that. |
| Permissions | `contents: read`, `pull-requests: write`. No PAT, no push. Its file tools are read-only. `run` is allowed (build and unit tests), but it is optional, because stage 4 and CI already ran the suite. |
| Identity | It posts as `github-actions[bot]`, a different account from the PR author (ADR-005), so its approve or request-changes is a real GitHub review. |

**Against approving everything.** The reviewer must output one entry per thing the issue asks for (`met` / `not met` / `cannot tell`, with evidence) before it gives a verdict. An approval that has an `issue requirement not met` entry is rejected by code (ADR-007).

**Against inventing problems.** Each finding must carry evidence: a file and line that is in the diff, or a command it ran and the output. Findings without valid evidence are dropped by code. Style-only remarks are labelled `nit` and do not count towards `request_changes`.

**Measurement.** Five seeded PRs (`experiment/seeded_prs/`) with known labels test the reviewer before it is trusted:

- four have planted defects (a wrong edge case, a missing requirement, a broken existing behaviour, a test that does not test the change),
- one is correct.

We report catches, misses and false alarms.

## Alternatives considered

- **Reviewer as a step inside the build job.** It would share the runner, the files written by earlier stages, and the credentials. Rejected.
- **Reviewer also sees the spec and design.** It would review against the same contract the implementer used, so a wrong spec would never be caught. Rejected: the issue is the ground truth.
- **Reviewer must always run the tests.** Stronger evidence, but it duplicates stage 4 and CI and costs extra calls. Kept optional.
- **"Find at least N problems" prompt.** Produces false alarms. Rejected in favour of the evidence rule.

## Consequences

- The reviewer judges against the issue, so it can disagree with the spec. That is intended, and these cases are reported in the results.
- A reviewer without the design can misread an intentional choice as a defect. The evidence rule and the human's final decision limit the damage.
- If Hydrogen is unavailable and the fallback model is the builders' model, independence is weaker for that run, and this is recorded (ADR-006).
