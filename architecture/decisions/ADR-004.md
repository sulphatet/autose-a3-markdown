# ADR-004: State on a dedicated branch, with deterministic resume

**Status:** Accepted
**Date:** 2026-11-21
**Decision area:** D4, state

## Context

State must survive in three situations:

- Between stages inside one run, which is easy because it is the same job.
- Between the build and review jobs.
- Between runs, because a review round starts a new run (ADR-002) and a crashed or cancelled run may be restarted.

Anyone must be able to follow a run on GitHub.

The reviewer must not see the spec, the design or the test report (ADR-008). Anything committed to the PR branch appears in the diff the reviewer reads, so the artifacts cannot live on that branch.

## Decision

1. **Run artifacts.** Every stage's artifact is uploaded with `actions/upload-artifact` as `autose-issue-<n>-round-<r>`. This is what a grader opens from the run page.
2. **Durable state branch.** The same files, plus `state.json`, are committed by the orchestrator to an orphan branch `autose-state` under `runs/issue-<n>/round-<r>/`. That branch never becomes a PR, is readable on GitHub, and is the source for resuming.
3. **Progress comment.** The orchestrator keeps one comment on the issue up to date, with a checklist of stages, links to the run and the PR, and the reason for any stop.
4. **Code branch.** The change itself lives on `autose/issue-<n>`. The branch name is deterministic, so a restart reuses it instead of opening a second PR.

`state.json` records, for each stage: status (`pending`, `passed`, `failed`, `stopped`), attempt count, the artifact's SHA-256, and an **input hash**. The input hash is a SHA-256 of everything the stage consumed: issue title and body, base commit, prompt version, model, and the hashes of upstream artifacts.

**Resume rule.** On restart, the orchestrator recomputes each stage's input hash in order. A stage is skipped only if it `passed` and its input hash matches. The first stage that does not match, or did not pass, runs again, and every later stage is marked `pending`. The code branch is rebuilt from base plus the last passing `diff.patch`, so a half-finished edit from a killed job never survives a restart.

If the issue is edited, its hash changes and the run starts from S1. That is the correct behaviour, because the requirements may have changed.

## Alternatives considered

- **Commit artifacts to the PR branch.** Visible next to the code, but the reviewer would see `design.md` and the test report in the diff, which breaks independence. Rejected.
- **Workflow artifacts only.** Simple, but they expire (90 days by default), and finding the previous run's artifacts means a search by run-id across runs.
- **Actions cache.** Caches can be evicted at any time and are meant for speed, not as the record of what happened.
- **Always restart from S1.** Simplest and always consistent, but it wastes calls on the free tier, and a run that failed in S5 because of flaky CI would redo all the agent work.

## Consequences

- Resuming is deterministic: the same inputs always skip the same stages.
- Two writers can conflict on `autose-state`. ADR-010's per-issue concurrency group stops two runs for the same issue writing at once, and different issues write to different folders.
- The orchestrator needs push rights to `autose-state`. It uses the job's `GITHUB_TOKEN`, not the PAT (ADR-005), because pushes to this branch must not trigger other workflows.
