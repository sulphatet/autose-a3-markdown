# ADR-007: Code decides every check; LLM output is only an input

**Status:** Stage 1 check superseded by ADR-015. Accepted. The `flake8 markdown passes` part of check 3 is superseded by ADR-013 (found in the first real run).
**Date:** 2026-11-21
**Decision area:** D7, checks

## Context

Every stage must pass a check before handing over. If the agent that did the work also decides whether it passed, a model that is wrong and confident passes its own mistakes.

Some checks are naturally mechanical, such as "the code builds" and "tests pass". Others sound like judgements, such as "acceptance criteria are testable" and "the plan names the files and functions". These can still be turned into mechanical checks if the artifact has a required structure.

## Decision

Each artifact has a required, machine-readable structure. A Python check function (`workflow/autose/checks.py`) returns pass or fail with reasons. The orchestrator, not an agent, records the result in the artifact and in `state.json`.

| # | Check | How it is carried out |
| --- | --- | --- |
| 1 | All acceptance criteria are testable | Parse the A1 skill's `VALIDATION.md` and `SRS.md`. **Pass** requires: the verdict is `READY FOR IMPLEMENTATION` or `PARTIALLY READY`; check `V-Q4` (every AC is pass/fail observable) is `PASS`; at least one `Must` requirement is `Ready`; every `Ready` requirement has at least one `AC-…` line in Given/When/Then form; no AC contains `<TBD` or a word from the skill's V-Q1 weasel-word list. The skill reports on itself, so code re-checks the structure instead of trusting the verdict alone. Only `Ready` requirements are passed on. |
| 2 | The plan names the files and functions | `design.md` must contain a "Change list" table (`file`, `symbol`, `change`, `ACs covered`). For each row, the file must exist, unless marked `new`. The symbol must be found by Python `ast` in that file (a function, class or method), unless marked `new`. Every Ready AC must be covered by at least one row. |
| 3 | The code builds | The diff is not empty, and touches nothing under `.github/` or the assignment folders. `pip install -e .` succeeds. `python -c "import markdown; markdown.markdown('# x')"` succeeds. `flake8 markdown` passes, the same lint as upstream CI. Files changed outside the design's change list are recorded in the artifact as a deviation, not a failure. |
| 4 | All new and existing tests pass | Every Ready AC has a test whose name contains its ID (for example `test_AC_FR_001_1`). **Fail-to-pass:** for bug and feature ACs, the new tests must *fail* on the base commit and *pass* on the branch. A test that passes on base does not test the change. Then the full suite, `python -m unittest discover tests`, must exit 0. |
| 5 | PR is open and CI passes | `gh pr view` shows the state is `OPEN`. `gh pr checks --watch` (with a time limit) shows every check passing. CI is the upstream CI, kept unchanged: the tox test matrix, the lint jobs and the changelog enforcer. A red CI goes back to S3 with the failing job's log. |
| 6 | Reviewer approves, or 2 rounds used | `review.json` must validate against a schema: verdict, `kind`, findings with evidence. Code drops findings whose evidence does not hold, such as a cited file or line that is not in the PR, or a command that was not run. A `request_changes` with no valid findings left is treated as invalid, and the reviewer is asked once more. After that, it counts as `approve` with a note. |

The upstream changelog enforcer is kept. The implementer must add a `docs/changelog.md` entry, as a human contributor would. This makes "CI passes" mean what it means for real contributors.

## Alternatives considered

- **LLM judge for each stage.** Easy to write, but a judge from the same model family tends to agree with the work. Its verdict also changes between runs. Rejected as the decider. LLM output is only used where judgement is unavoidable: the spec content and the review findings, and even those are validated structurally.
- **Trust the A1 skill's verdict as is.** The skill validates itself. That is useful, but it is the same model grading its own work, so code re-checks the structure.
- **Remove the changelog enforcer and the flaky lint jobs from CI.** Higher pass rate, but CI would no longer be the project's real CI. Rejected. CI failures unrelated to the diff (such as `checklinks` network errors) are recorded as such in `results.csv`.

## Consequences

- Every pass or fail can be reproduced by running the check script on the stored artifacts.
- Structural checks can be passed by an artifact that is well-formed but wrong, for example a test named after an AC that does not really test it. The fail-to-pass rule and the independent review are the protection against this.
- Strict formats cause failures that are only about format. The prompts include the exact format, and a format failure is returned to the same agent once before the stage counts as failed.
- The human makes the final merge decision. No check merges anything.
