# ADR-010: Triggers, who may trigger, and concurrent runs

**Status:** Accepted
**Date:** 2026-11-21
**Decision area:** D10, triggers

## Context

Runs cost quota and push code, so only maintainers should be able to start them. GitHub runs `issues` and `issue_comment` workflows for every event, whoever caused it, so the workflow must check the actor itself.

Two runs for the same issue would race on the same branch, PR and state folder.

Comments the bot posts must not start new runs. Comments made with the PAT *do* trigger workflows, unlike those made with `GITHUB_TOKEN`.

## Decision

| Event | Condition | Effect |
| --- | --- | --- |
| `issues: labeled` | label is `autose`, and the sender has `triage`, `write`, `maintain` or `admin` permission (checked through the collaborators permission API) | Full pipeline from S1, or resume (ADR-004) |
| `issue_comment: created` on an issue | body starts with `/autose`; `author_association` is `OWNER`, `MEMBER` or `COLLABORATOR`; author is not a bot | Full pipeline, or resume |
| `issue_comment: created` on a PR | same conditions, and the PR's head branch starts with `autose/` | **Review only.** The review job runs again against the current PR head. This lets a maintainer push a fix themselves and ask for a new review. It does not count towards the two automated review rounds. |
| `workflow_dispatch` | inputs `issue`, `round`, `resume_from` | Internal: used by the review job to start the next round. Also available for manual reruns. |

A `gate` job runs first. It has no secrets and only `issues: read` permission. It checks the conditions above and outputs the issue number and mode. Untrusted or unrelated events end there, at almost no cost.

**Concurrency:** `concurrency: { group: autose-issue-${{ issue number }}, cancel-in-progress: false }`. A second trigger for the same issue waits until the first one finishes, and then resumes from saved state. Cancelling the first run would waste the agent work it had already done. Different issues run in parallel, but the Gemini rate limit is per project, so the experiment runs are started one at a time.

Bot comments are posted only with `GITHUB_TOKEN`, and the gate ignores bot authors, so the bot can never trigger itself.

## Alternatives considered

- **Any commenter can type `/autose`.** Lets anyone spend the quota and push branches. Rejected.
- **`cancel-in-progress: true`.** The latest request wins, but agent work already paid for is thrown away, and a half-pushed branch could be left behind. Rejected. Resume makes the queued run cheap.
- **`/autose` on a PR re-runs the whole pipeline.** Redoes spec and design that were already reviewed. Rejected: the maintainer's comment on a PR is about the change under review.
- **`pull_request_target` events.** Run with secrets for code from forks, which is a well-known source of attacks. Not used.

## Consequences

- Only the repository owner and collaborators can start or re-review runs.
- A maintainer's manual fix plus `/autose` on the PR gets an independent review without restarting the pipeline.
- Queued runs on the same issue resume in order, so the result is the same as if they had been started one after the other.
