# ADR-015: Stage 1 passes on any testable acceptance criterion; the A1 verdict is advisory

**Status:** Accepted. Supersedes the stage 1 check in ADR-007 (verdict, V-Q4, "Ready `Must`" and weasel-word rules).
**Date:** 2026-11-22
**Decision area:** D7, checks; A1 skill adaptation

## Context

ADR-007 made stage 1 pass only if the A1 skill's own verdict was READY or PARTIALLY READY, V-Q4 was PASS, and at least one `Must` requirement was `Ready` with clean ACs.

Under that rule the real runs stopped three of the four clear issues at stage 1:

| Issue | Prompt | What the spec agent did |
| --- | --- | --- |
| #3 | v2 | asked whether the reported behaviour is "intended" |
| #5 | v2 | invented a question about configurability, marked everything Needs-Clarification |
| #3 | spec-v3 (E2 variant B) | P1 question about the output structure, although the issue states it ("show up as its own footnote") |

Rule 5a in spec-v3 tried to fix this with more prompt rules. It did not work on Flash-Lite. Each round of extra rules made the stage more complex and still stopped clear issues.

In all three cases the spec agent **had** written a usable AC (for example #3: given the nested footnote input, the output contains "Second" in the footnotes list). Only the verdict and the readiness labels blocked it. The course asks for a pipeline that works end to end, not a strict requirements gate.

## Decision

The stage 1 check (`checks.check_spec`) now passes when the spec has **at least one testable acceptance criterion**:

- the AC has *given* and *when*, and its expected result (after *then*) names something concrete: a quoted or backticked literal, or a number;
- `<TBD: Q-n>` markers are removed; an AC whose result is only a TBD is skipped;
- ACs of `Ready` requirements are used if any exist, otherwise all ACs.

The A1 verdict is still produced and written into the stage artifact, but it no longer decides. Open questions are kept in REGISTER.md as assumptions that the reviewer and the human merger can see. The only format retry left is "no verdict at all".

The spec prompt (v2) and the A1 skill are unchanged.

## Alternatives considered

- **Keep tuning the prompt (spec-v3, v4, ...).** Tried once (E2 variant B) and it failed; the model keeps asking. More rules mean more cost and still no guarantee.
- **Skip stage 1 for issues that look clear.** Needs a classifier that is itself an agent decision.
- **Keep the strict gate.** It is the "right" requirements-engineering answer, but it stops most real issues, so the rest of the pipeline never gets exercised.

## Consequences

- Checked on the saved stage 1 outputs of earlier runs (no new model calls): #2, #3, #4 and #5 pass; the vague #6 still stops, because its ACs say only "unspecified smart handling `<TBD: Q-1>`".
- The pipeline may now build on an assumption the reporter would reject. The safety net is the reviewer, the hidden tests and the human who merges.
- The A1 skill becomes advisory: its questions are documented, not enforced. This is adaptation row 13 in `architecture/a1_skill_adaptation.md`.

## Amendment (2026-11-23, run 45016653708)

In the real lenient run on the vague issue #6, stage 1 **passed**. Its only AC was "then `<TBD: Q-02>` (blocked by open question Q-02)". After the TBD marker was removed, the digits in the question ID `Q-02` counted as "a number in the expected result". The check on saved specs had not shown this, because that earlier spec was worded differently.

Fix: requirement, question and source IDs (`Q-`, `FR-`, `NFR-`, `AC-`, `ASM-`, `SRC-`), and any bracketed note that contains one, are removed before the "concrete result" test. On all saved specs: #2-#5 still pass, #6 stops.

Lesson: a lenient rule needs negative test cases as much as positive ones.
